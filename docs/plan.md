# 西成泥酔旅行 TS版リビルド 工程計画 v0.4

作成: 2026-11-13 / 更新: 2026-11-14
対象: [nao-enpg/Nishinari_Izakaya_Crawl](https://github.com/nao-enpg/Nishinari_Izakaya_Crawl)（Rails 7.1）を TypeScript で作り直し、Cloudflare で公開する

改訂履歴
- v0.2: Hotwire をやめ、React Router v8＋shadcn/ui に変更
- v0.3: 認証を Firebase Authentication に変更
- v0.4: 独立レビューの指摘を反映した。あわせて次を変更した

  - Workers は有料プランを前提にした

## 0. 決定済みの前提

| 項目 | 決定内容 |
| --- | --- |
| 忠実度 | 機能・画面の構成・文言・URL（番号を含む）は現行どおりにする。見た目は多少変わってよい。権限漏れなどのバグは直し、使われていないコードは移植しない。現行との違いはすべて「差分台帳」に記録し、Nao が承認する |
| フレームワーク | React Router v8（フレームワークモード、サーバー描画）＋React 19。Vite 8 でビルドし、`@cloudflare/vite-plugin` で Cloudflare Workers にデプロイする。雛形は `npm create cloudflare@latest -- --framework=react-router` から作る |
| UI | Tailwind CSS v4＋shadcn/ui |
| 実行環境 | Cloudflare Workers の**有料プラン（月 $5〜）**。無料プランは CPU 10ms・外部呼び出し50件までで、足りないため |
| DB | Cloudflare D1。作成時に `--location apac` を指定する。ORM は Prisma 7.10 系に固定し、Prisma 8（RC）は使わない。原子性が必要な処理は Prisma ではなく D1 の `batch()` で書く（第1章を参照） |
| データ | 現行の本番 DB（Koyeb の PostgreSQL、米国東部）を移行元にして D1 へ移す。移すのは自前のデータだけ（店の番号・名前・紹介文・タグ、ユーザー、旅程表、お気に入り）。Google 由来のデータ（座標・住所・写真 URL・営業時間）は移さない。店の一覧は Nao の最新の保存済みリストに合わせ、旧 DB と突き合わせる。**店・旅程表の番号は現行のまま引き継ぐ** |
| 認証（**追加改修**） | Firebase Authentication の Google ログインだけを使う。匿名ユーザーは使わない。Firebase は Maps 用とは別のプロジェクトにし、課金なしの Spark プランで運用する。Identity Platform にはアップグレードしない。サーバー側では ID トークンを `jose` で検証し、自前の httpOnly セッション Cookie を発行する（セッションは D1 に保存）。旧ユーザーは、初めてログインしたときに Google アカウントの ID で旧データと紐付ける |
| Google Maps の規約 | 無期限に保存するのは place_id と自前のデータだけ。座標は30日以内に自動で更新する。写真は表示のたびに API から取得する。営業時間と閉業の表示は**追加改修**として入れる |
| 公開 | 稼働中の nishinari-izakaya.net を新サイトに切り替える |
| 体制 | GitHub を Claude と連携し、Claude が push と PR 作成を担当する。デプロイは GitHub Actions から行う |
| 設計手法 | spec-kit 1.4.0（リリース版に固定）を Claude Code 統合で使う |

## 1. 調査で分かった、計画に影響する事実

### データ
- 現行の本番 DB は Koyeb で稼働している。居酒屋・タグ・紹介文・Googleマップ URL・旧番号は、この DB と公開ページにしか無い（リポジトリの CSV は見出し行だけ）。
- 旧 DB には place_id が無い。そのため、店ごとに place_id を探して付ける必要がある。
- 旧 DB の `authentications.uid` には Google アカウントの ID が入っている見込み。Firebase の ID トークンにも Google アカウントの ID が含まれるので、旧ユーザーと新しいログインを紐付けられる（P1 で実データを見て確認する）。

### 現行のバグ（修正して、差分台帳に載せる）
- 権限チェックの漏れ: 他人の旅程表を編集・削除できる。他人の旅程表にも、店の追加・削除・並べ替えができる。
- 翻訳キーの誤り: `plofiles` のスペルミス、非公開の旅程表を開いたときのキー、英語の画面で削除の確認ダイアログが日本語になる。
- 言語の指定（`?locale=`）が消える箇所が5か所ある。`?locale=fr` のような値を渡すと 500 になる。
- 未ログインで要ログインのページを開くと、`/login` へ転送されたあと 406 で空白のページになる。
- プロフィールの名前を同じ画面で2回編集すると、画面が壊れる（推定）。
- お気に入りを2回押すとエラーになる（推定）。DB に一意制約が無いため。
- 地図を開かなくても、一覧を開くたびに地図が初期化されて課金される。
- ライトモードで白い文字が読めない（推定）。
- 全22項目の一覧は、レビューの報告書の 3.4節にある。P1 の現行仕様台帳に取り込む。

### 使われていないコード（移植しない）
- users と sessions のコントローラ、user_sessions の new と create。ただし**ログアウト（`DELETE /logout`）は使われているので移植する**。
- `izakayas#favorites`（呼んでいるメソッドが存在せず、どの場合も 500 になる）
- React と MUI、ActionCable、`map.js`、`modal` コントローラ、jQuery、使われていない gem と列

### 技術的な制約
- **Prisma＋D1 のトランザクションは、エラーにならないまま原子性が無い**。アダプター 7.10.1 の commit と rollback は何もせず、`$transaction` も1文ずつ実行される（ソースで確認済み）。原子的に動くのは D1 の `batch()` だけ。
  - 並べ替え、旅程表の削除、移行の取り込みは、`batch()` か1本の SQL で書く。
  - `prisma.$transaction` は lint で禁止する。
- **D1 のマイグレーションでデータが消えることがある**。D1 では外部キーの強制を止められないため、Prisma がテーブルを作り直す SQL を出すと、連鎖削除で子の行が消える。
  - 生成した SQL に親テーブルの `DROP TABLE` が含まれていないかを CI で検査する。
  - 適用は `wrangler d1 migrations` で行う。
  - データの取り込みは「全削除して入れ直す」ではなく、upsert で行う。
- 旧 Places API は原則として新しいプロジェクトでは使わない（Legacy 扱い）。Places API (New) を使う。
- 現行の部分更新（お気に入り、名前のその場編集、並べ替え）は Turbo に頼っている。React Router では loader / action と `useFetcher` で作り直す。
- Rails が既定で付けていたセキュリティヘッダー（HSTS は2年・サブドメイン込み）は、自前で同じように付ける。

### 表示時に API から取得するときの費用
- 写真を出している画面は5つある（居酒屋一覧・詳細、旅程表一覧・詳細、マイページ）。写真1枚の表示には、Place Details（写真の一覧は無料の SKU）と写真の取得（月1,000件まで無料、超えると1,000件あたり $7）の2回の呼び出しが要る。
- 写真を返す口は誰でも呼べるので、対策をしないと課金を増やされる。Google Cloud の予算アラートは通知するだけで、課金を止めない。
- 対策（必須）
  - 写真はカードごとに遅延読み込みする。
  - DB にある店だけを受け付ける。
  - レート制限をかける。
  - アプリ側で日次の件数を数え、上限を超えたら代替画像を返す。
  - Bot には代替画像を返す。
  - 写真をキャッシュしない（規約）。
- 写真や Places のデータを出す画面では、Google のロゴと写真撮影者の表示が必要。

### Firebase Authentication（公式ドキュメントで確認済み）
- アップグレードしなければ、Google ログインの1日あたりの利用者数に上限は無い。
- 課金アカウントを紐付けると Blaze プランに自動で切り替わる。そのため、Maps 用とは別のプロジェクトにする。
- 2026-10-15 以降に作ったプロジェクトでは、authDomain（`<サイトID>.firebaseapp.com`）のサイト ID にランダムな文字が付くことがある。また、`localhost` が承認済みドメインに既定では入らない。
- Firebase Hosting 以外でリダイレクト方式のログインを使う場合、`/__/auth/*` を authDomain へ透過的に中継する必要がある。302 で転送してはいけない。
- 汎用の JWT ライブラリで ID トークンを検証するときは、alg・kid・aud・iss・exp・iat・sub・auth_time をすべて自前で確認する。公開鍵は X.509 形式で配られ、Cache-Control の max-age に従って更新する。

### spec-kit
- 公式の流れは、constitution を1回作ったあと、**機能ごとに** specify から converge（Converged になるまで）までを回すこと。全機能の設計を先に揃える形ではない。
- 今どの機能を扱っているかは、ブランチではなく `.specify/feature.json`（git の管理外）で決まる。セッションをまたぐときは、`SPECIFY_FEATURE_DIRECTORY` を設定する。
- spec of specs（ロードマップで機能を分ける方式）は、軽い方法で足りないときの選択肢。今回は複数の機能を作るので使う。

## 2. 全体の流れ

Nao さんが挙げた「調査 → 設計 → 設計レビュー → 実装 → 実装レビュー → デプロイ」のうち、設計から実装レビューまでは**機能ごとに繰り返す**。その前後に、準備・データ移行・統合検証・切り替え後の運用を加えた。

| # | 工程 | 主な成果物 | 次へ進む条件 |
| --- | --- | --- | --- |
| P0 | 環境準備 | 新リポジトリ、各種アカウントとキー、版の固定表、CI の雛形 | Actions から staging への空デプロイが通る |
| P1 | 調査 | 現行仕様台帳、差分台帳 v0、基準の採取、技術検証の結果、費用試算、旧 DB の調査 | Nao のレビュー |
| P2 | データ移行の準備（P1 と並行） | 移行スクリプト、店の突き合わせ表（place_id つき）、タグと紹介文の CSV | staging への移行リハーサルで件数が一致する |
| P3 | 全体設計 | constitution、ロードマップ、F1 の plan（システム全体の設計） | Nao の承認 |
| P4 | 機能ごとの開発（F1〜F6 を順に） | 機能ごとの spec / plan / checklist / tasks / 実装 / PR | 各機能が Converged になり、レビューを通ってマージされる |
| P5 | 統合検証 | 現行との比較結果、セキュリティ確認、性能と費用の実測 | 現行との差分が台帳と一致する |
| P6 | ステージング・受け入れ・リハーサル | 受け入れテストの記録、切り替えのリハーサル記録 | Nao の受け入れ OK |
| P7 | 本番切り替え | 切り替え手順書、ロールバック手順書 | スモークテスト OK |
| P8 | 切り替え後の運用 | 監視、定期ジョブ、旧環境の停止 | ロールバック期限の後、旧環境と旧データを削除する |

### P4 の1機能あたりのサイクル（ここが「設計 → 設計レビュー → 実装 → 実装レビュー」）

1. **設計**: `/speckit-specify`（現行仕様台帳の該当する節を根拠にする）→ `/speckit-clarify`（判断が必要な点は Nao に質問する）→ `/speckit-plan` → `/speckit-checklist`（観点: 現行との同等性、セキュリティ、i18n、Google の規約）→ `/speckit-tasks`
2. **設計レビュー**
   - `/speckit-analyze` を、指摘が無くなるまで繰り返す。
   - 現行仕様台帳の該当項目が、すべて要件か差分台帳に対応しているかを確認する。
   - 設計に関わっていないサブエージェントがレビューする。
   - Nao がチェックリストに `[x]` を付けて承認する。
3. **実装**: `/speckit-implement` をフェーズ単位で区切って実行する。テストを先に書く。
4. **実装レビュー**
   - `/speckit-converge` を Converged になるまで、implement と交互に繰り返す。
   - 現行との比較 E2E と、セキュリティのテストを流す。
   - 独立したサブエージェントと Nao がコードレビューをする。
5. **マージ**: 1機能 = 1ブランチ = 1PR。マージしてから次の機能に進む。

## 3. 各工程の詳細

### P0 環境準備
- **GitHub（Nao）**: Claude との連携を有効にし、新リポジトリを作る。main ブランチは保護する。
- **Cloudflare（Nao）**
  - Workers の有料プランに入る。
  - API トークンを発行する。権限は Workers と D1 だけにする。
  - D1 を staging 用と本番用の2つ、`--location apac` で作る。
  - nishinari-izakaya.net の DNS の管理先、DNSSEC、MX・TXT レコードを確認する。Cloudflare 以外なら、全レコードを複製したうえでネームサーバーの移管を早めに始める。
- **Google Cloud（Maps 用、Nao）**
  - Places API (New) と Maps JavaScript API を有効にする。地図用の Map ID を作る。
  - API キーをブラウザ用（リファラー制限）とサーバー用（API 制限）に分ける。
  - 予算アラートと、API ごとの日次クォータ上限を設定する。
- **Firebase（Nao）**
  - Maps 用とは別のプロジェクトを Spark プランで作る。作成後、Identity Platform にアップグレードされていないことを確認する。
  - Google ログインを有効にする。
  - 承認済みドメインに、本番・staging・localhost を登録する。
  - Firebase 側の OAuth クライアントに、`https://<各ドメイン>/__/auth/handler` をリダイレクト URI として登録する。
  - 同意画面のアプリ名・プライバシーポリシー・利用規約の URL を設定し、公開ステータスが「本番」になっていることを確認する。
- **旧 DB への接続情報（Nao）**
  - パスワードはチャットに貼らず、GitHub Secrets に登録する。
  - 移行スクリプトは GitHub Actions か Nao の PC で実行する（この作業環境からは Postgres に直接つなげない見込み）。
- **リポジトリの雛形（Claude）**
  - C3 で React Router の雛形を作り、上の表のとおりに版を固定する。
  - `uv tool install specify-cli==1.4.0` の後、`specify init --here --force --non-interactive --integration claude --script sh` を実行する。
  - CLAUDE.md に、spec-kit の機能の切り替え手順（`SPECIFY_FEATURE_DIRECTORY`）を書く。
  - GitHub Actions を用意する。順番は、型チェック・lint・テスト → D1 マイグレーション → `wrangler deploy`。
- **完了条件**: Claude が push でき、Actions から staging に Hello World がデプロイされる。

### P1 調査
1. **現行仕様台帳**（`docs/legacy/`）
   - ルート、画面、状態ごとの表示、クライアント側の挙動、外部への依存、SEO / OGP、言語の切り替えを記録する。
   - レビューの報告書 3.4節の22項目を取り込む。
2. **差分台帳 v0**（`docs/deviations.md`）
   - バグの修正、移植しないもの、意図的な追加・変更を1件ずつ記録する。意図的な追加・変更には、Firebase 認証、営業時間の表示、地図の読み込み方、規約とプライバシーポリシーの更新が含まれる。
3. **基準の採取**
   - 現行コードを GitHub Actions 上で**本番モード**で起動する。必要な準備は次のとおり。
     - `force_ssl` と `config.hosts` への対処
     - `SECRET_KEY_BASE` の設定
     - テスト用のログイン回避（リポジトリにはコミットしない）
     - テストデータの投入
     - GA と Maps への通信の遮断
   - Playwright で、ja / en、PC 幅 / スマホ幅、ライト / ダークの状態を撮影し、画面の構成・文言・遷移・ステータスコードを記録する。
4. **旧 DB の調査**（読み取りのみ）
   - テーブルごとの件数を数える。
   - `authentications.uid` の形式（Google アカウントの ID か）を確かめる。
   - 番号の最大値、`row_order` の値の分布、重複したお気に入りの有無を調べる。
5. **技術検証**（試作コードは捨てる前提）
   - a. React Router v8 の雛形が、ローカルと staging で動くか。Worker の入口に Cron を同居させられるか。**SSR＋Prisma の CPU 時間を実測する**。
   - b. Prisma 7.10＋D1 で、多対多の関係とタグの AND 検索が動くか。Vite でのバンドルに問題がないか。
   - c. 並べ替えを `env.DB.batch()` で書き、途中で失敗したときに巻き戻ることをテストで再現する。
   - d. Firebase の Google ログインの一連の流れ
     - `/__/auth/*` の中継: 中継先は実際の authDomain にする。リダイレクトは自分でたどらずブラウザへ返す。キャッシュしない。セキュリティヘッダーを上書きしない。自ドメインの Cookie を転送しない。
     - リダイレクト方式とポップアップ方式を、iPhone の Safari と Android の Chrome で試す。
     - ID トークンを検証し、セッションを作る口で CSRF 対策と auth_time の確認をする。
     - 旧ユーザーとの紐付け（Google アカウントの ID）。
   - e. Places API (New) の Text Search・Place Details・写真の取得を Workers から呼べるか。テイクアウトの URL にある CID と、`googleMapsUri` の cid で照合できるか。
   - f. `useFetcher` でお気に入りと並べ替えを作り、楽観的更新が自然に動くか。スマホのタッチ操作でドラッグ＆ドロップが動くか。
   - g. 多言語化の方式（`?locale=` を維持できるか）。ライブラリの版が衝突しないか。
   - h. shadcn/ui で画面を1枚作り、見た目の方向性を Nao と合わせる。
6. **費用の試算**
   - GA4 でアクセス数を確認する。
   - 写真を出す5画面とクローラーを含めて月額を出し、日次上限の値を決める。
- **完了条件**: Nao が台帳・差分台帳・技術検証・試算をレビューする。

### P2 データ移行の準備（P1 と並行）
1. **旧 DB から取り出す**: Nao の PC か GitHub Actions で実行する。個人データ（メールアドレス）を含むので、出力をリポジトリにコミットしない。使い終わったら削除する。
2. **店の突き合わせ**
   - Nao がテイクアウトで保存済みリストを書き出す。
   - 取り込みスクリプトで、旧 DB の店と最新の保存済みリストを突き合わせる。照合は店名と CID で行う。
     - テイクアウトの CSV は、先頭に説明行が入る場合と、古い `Tags` 列がある場合に対応する。
   - 店ごとに place_id を付ける。照合できなかった店は確認リストに出し、Nao が判断する。
3. **移行データの作成**
   - 店: 番号、Nao が確定した店名、紹介文、タグ、表示順、place_id、非表示フラグ（リストから外れた店）。
   - 移さないもの: 座標・住所・写真・営業時間（Google のデータ）、パスワード関連の列。CSV にも git の履歴にも入れない。
   - ユーザー・旅程表・お気に入り: 番号と作成日時を保つ。並べ替えの値は順番を保って振り直す。重複したお気に入りは1件にまとめる。
4. **取り込み**: `batch()` による upsert で行う。新しい番号は旧番号の最大値の続きから振る。
5. **検証**: staging でリハーサルし、件数・関連・並び順が旧 DB と一致することを自動で確かめる。CI では、CSV の形式・重複・禁止列が無いことを検査する。

### P3 全体設計
1. **`/speckit-constitution`**: 原則の案
   - 現行との同等性を最優先する。違いは差分台帳に記録して承認を得る。
   - Google Maps Platform の規約を守る（保存してよいデータ、ロゴと撮影者の表示、キャッシュの禁止）。
   - Workers と D1 の制約の範囲で作る。原子性は `batch()` で確保し、`$transaction` は使わない。
   - テスト: 全ユーザーストーリーに E2E テストを書き、ドメインロジックは単体テストで先に書く。
   - セキュリティ: 書き込みを伴うすべての操作で所有者を確認する。CSRF 対策、セキュリティヘッダー、秘密情報は Secrets で管理する（`VITE_` で始まる変数に入れない）。
   - ja / en の両対応を必須にする。
   - 外部 API が上限に達しても、表示を劣化させてサービスは止めない。
2. **ロードマップ**（`ROADMAP.md`）

   | ID | 機能 | 範囲 | 依存 |
   | --- | --- | --- | --- |
   | F1 | 基盤と静的ページ | 共通レイアウト、ヘッダー、フッター、フラッシュ、言語切り替え、トップ・規約・プライバシー・問い合わせ（規約とプライバシーポリシーの更新を含む）、SEO / OGP / GA、エラーページ、セキュリティヘッダー | ― |
   | F2 | データ層と移行 | Prisma スキーマ、D1 マイグレーションの運用、移行スクリプトの本実装、座標の定期更新、Places API クライアント、写真の取得口（費用の対策つき） | F1 |
   | F3 | 認証とマイページ | Firebase の Google ログイン、`/__/auth` の中継、トークン検証とセッション、旧ユーザーとの紐付け、ログアウト、要ログイン時の誘導、名前のその場編集、マイページの一覧 | F2 |
   | F4 | 居酒屋 | 一覧、店名検索、タグの AND 絞り込み、地図、近い10件、詳細、外部リンク、お気に入りの切り替え | F3 |

3. **F1 の plan をシステム全体の設計にする**: ディレクトリ構成、URL の互換表（`/logout` を含む）、レイアウトとテーマ、スキーマ、認証、CSRF、i18n、環境変数、CI/CD、テスト基盤。F1 を実装して確かめてから固める。
4. **スキーマの方針**
   - izakayas: 番号は旧番号を保つ。`place_id` は一意。表示順と非表示フラグを持つ。座標と取得日時を持つ（30日で更新、期限切れは使わない）。住所・営業時間・写真の参照は保存しない。
   - users: 番号は旧番号を保つ。`firebase_uid` は一意。旧ユーザーとの紐付け用に Google アカウントの ID を持つ。メールアドレスをいつまで持つかは F3 の clarify で決める。
   - sessions: セッション ID のハッシュ、ユーザー、有効期限。
   - favorites: (user, izakaya) の組を一意にする。
   - 子の行の削除はアプリ側で `batch()` を使い、子から親の順に行う。DB の連鎖削除に頼るかは、P1 で比べて決める。

### P5 統合検証
- **現行との比較**: P1 で採取した基準と新しい実装に、同じ Playwright シナリオを流す（画面の構成、文言、遷移、ステータスコード、URL）。違いは差分台帳に載っているものだけであることを確認する。スクリーンショットは Nao の目視確認に使う。
- **セキュリティ**: 他人の旅程表やお気に入りを操作できないこと、CSRF、XSS、セキュリティヘッダー、秘密情報の扱い。
- **性能と費用**: CPU 時間、API の呼び出し回数、写真の取得口が悪用されないこと。

### P6 ステージング・受け入れ・リハーサル
- staging に、旧 DB から移行したデータを入れる。staging には noindex を付け、アクセス制限をかける。
- Nao がスマホの実機で受け入れテストをする（ja / en、Google ログイン、旧アカウントの引き継ぎ、地図、現在地、タッチでのドラッグ＆ドロップ）。
- 本番切り替えを、手順書どおりにリハーサルする（移行、件数の確認、切り替え、ロールバック）。
- 旧サイトに告知を出す（遅くとも切り替えの2〜4週間前）。内容は、切り替えの日時、停止時間、ログイン画面が変わること。

### P7 本番切り替え
1. **事前準備**
   - DNS の TTL を短くする。
   - 本番の Secrets を登録する。
   - Maps API キーのリファラー制限と、Firebase の承認済みドメイン・リダイレクト URI を確認する。
   - 現行の OAuth クライアントは、ロールバックに備えて残す。
2. **旧サイトを停止中にして、最終移行をする**
   - 旧サイトをメンテナンス表示にする（書き込みを止める）。
   - 旧 DB から最終的なデータを取り出し、本番 D1 に取り込み、件数を確かめる。
3. **切り替え**: Workers のルートかカスタムドメインに nishinari-izakaya.net を割り当てる。カスタムドメインの場合は、既存の CNAME を先に消す必要がある。HSTS のため、証明書の発行が間に合うことを staging で事前に測っておく。
4. **スモークテスト**: ログイン、旧アカウントの引き継ぎ、検索、旅程表。
5. **ロールバック**
   - 条件・期限・手順を手順書に書く。
   - Koyeb 側のカスタムドメインと証明書は有効なまま残す。
   - ロールバックすると、切り替え後に作られたデータは旧サイトに戻らない。その旨を告知に含める。

### P8 切り替え後の運用
- **監視**: Workers のログとエラー、外形監視、Google Cloud の予算アラート、Cron の失敗通知、取得から25日を過ぎた座標の警告。
- **定期ジョブ**: 座標の30日ごとの更新（期限切れの座標は自動で消す）、place_id の年1回の更新、期限切れセッションの削除。
- **バックアップ**: D1 の Time Travel（有料プランで30日）から一度復元を試しておく。
- **旧環境の片付け**（ロールバック期限の後）
  - Koyeb のアプリと DB を停止する。DB のバックアップや手元のコピーも削除し、削除日を記録する。
  - 旧 Maps キーと旧 OAuth クライアントを削除する。
  - DB のパスワードなどのシークレットを無効にする。
- **spec の扱い**: spec は残し、次の改修の土台に使う。

## 5. 主なリスク

| リスク | 影響 | 対策 |
| --- | --- | --- |
| 写真の表示による Places API の費用と、取得口の悪用 | 高 | 遅延読み込み、DB にある店だけ受け付ける、レート制限、日次上限、代替画像、Bot 対策 |
| Prisma＋D1 で、原子性が無いことに気づかず実装する | 高 | `$transaction` を lint で禁止し、`batch()` の巻き戻りをテストで保証する |
| D1 のマイグレーションや再投入で、データが消える | 高 | 生成 SQL の検査、本番の複製での事前適用、upsert のみ、Time Travel |
| 本番切り替え時の DNS・証明書・HSTS・Firebase の設定ミス | 高 | 手順書、staging での事前計測、リハーサル、ロールバック手順 |
| 最終移行の間に旧サイトへ書き込まれたデータが失われる | 中 | 切り替え中は旧サイトをメンテナンス表示にする |
| 旧ユーザーの紐付けに失敗し、旅程表が見えなくなる | 中 | P1 で uid の形式を確認し、E2E テストで保証する。紐付けできなかった場合の救済手順を用意する |
| 移行データの扱いによる個人情報の漏えい | 中 | 取り出したデータはコミットしない、Secrets で管理する、使用後に削除する、ログに出さない |
| ブラウザの第三者ストレージ制限でログインが失敗する | 中 | `/__/auth/*` の中継、iPhone の Safari での実機検証 |
| 依存ライブラリの版の取り違え | 中 | 版の固定表、CI での版の一致確認、古い記事を参照しない |
| Google の表示義務（ロゴ、撮影者）を満たさない | 中 | 画面ごとの表示位置の表を作り、checklist に入れる |
| 店名の照合ミス | 中 | CID での照合、照合できない店は Nao が確認する |
